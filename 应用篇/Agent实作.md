# 应用篇二 · Agent 实作：模型 + 工具 + 循环

> 位置：接在 [小模型实作篇](小模型实作.md) 后面。上一篇讲模型本身怎么回事，这一篇讲怎么把模型装进一个能干活的程序里。学完你会明白：市面上各种 Agent 框架，拆开看都是这几样东西。

## 先把概念说清

### Agent 是什么

先说模型本身能干什么：你给它一段文字，它回你一段文字。仅此而已。它不能查时间，不能算账，不能读你硬盘上的文件，更不能记得你昨天说过什么。

Agent（智能体）就是在模型外面套了一圈程序，让它能真正办事。一句话拆开：

**Agent = 模型 + 工具 + 循环**

- **模型**是大脑，只负责想和说。
- **工具**是手：计算器、搜索、读文件、查数据库、调别的程序接口，都算工具。
- **循环**是节奏：模型想一步 → 决定用哪个工具 → 程序真的去执行 → 把结果递回给模型 → 模型接着想下一步。转很多圈，直到任务完成。

所以 Agent 不是一种新模型，还是一篇篇论文里那个语言模型（见本仓 [第三卷](../第三卷-Transformer与大模型.md)）；多出来的全是工程。把这句话记牢，后面所有框架在你眼里都会现原形。

### ReAct：想一步，做一步，看一眼

循环具体怎么转，有个经典套路叫 ReAct（Reasoning + Acting，推理 + 行动），出自 Yao 等人 2022 年的论文《ReAct: Synergizing Reasoning and Acting in Language Models》（arXiv:2210.03629）。这篇论文已补入本仓第三卷（见[第三卷 · ReAct 条目](../第三卷-Transformer与大模型.md)）——它实在是 Agent 的地基论文，绕不过去。

它的做法就是把三件事交替着来：

1. **Thought（想）**：模型先用一句话说清自己现在的判断和下一步打算。
2. **Action（做）**：模型发出一个具体动作，比如"查一下这个词"。
3. **Observation（看）**：程序执行动作，把真实结果递回去。

如此循环。为什么非要交替？只想不动，模型容易一条道走到黑、编造事实（这正是思维链的老毛病）；只动不想，又成了没头脑的脚本。想一步、做一步、用真实结果校正下一步——和人干活的节奏其实一样。

它在仓内的亲戚是第三卷的 [思维链 Chain-of-Thought（2022）](../第三卷-Transformer与大模型.md)：CoT 教模型"先想再答"，ReAct 在此基础上加了"想完可以伸手去查、去算"。另外，模型能"听懂指令、按要求办事"这件事本身，是 [InstructGPT](../全文精译/08-InstructGPT-2022.md) 那条线训出来的，没有它，工具调用根本无从谈起。

### 工具调用是怎么实现的

原理朴素得很，一点都不神秘：

1. 你在提示词里把可用工具列清楚：每个工具叫什么、干什么用、需要什么参数。
2. 模型觉得该用工具时，不直接回答，而是输出一段结构化的数据（现在主流 API 都支持原生的 function calling / tool use，模型会按约定格式吐出"工具名 + 参数"的 JSON）。
3. 你的程序解析这段数据，真的去调用那个函数，把返回值拼回对话里。
4. 模型看到返回值，继续往下想或直接给最终答复。

看清楚：**模型从头到尾只输出文字，是你的程序在真正执行**。模型说"删掉这个文件"，文件不会自己消失，除非你的程序照着做了。这也是为什么 Agent 的安全边界在程序这一侧，不在模型那一侧。

### 记忆：短期靠窗口，长期靠外存

- **短期记忆**就是当前对话的历史。模型没有真正的记忆，你每次调用 API 时把之前的对话一并传过去，它才"记得"聊过什么。对话窗口（context window）有长度上限，聊太长，前面的会被挤掉或截断——很多"AI 聊着聊着失忆了"都是这个原因。
- **长期记忆**是工程手段：把值得记的东西存到外部（文件、数据库），下次对话时按需取回来塞进提示词。它和下面要讲的 RAG 是同一套机制，只是一个存"关于用户的事实"，一个存"文档知识"。

### RAG：给模型配一本可以现查的资料

RAG（Retrieval-Augmented Generation，检索增强生成）解决一个实际问题：模型的知识停在训练结束那天，而且不知道你公司的事、私人的事。现训一个模型不现实，于是换个思路——**开卷考试**：

1. 提前把你的文档切成小段（chunking）；
2. 每段用一个 embedding 模型变成一串数字（向量），存进向量库；
3. 用户提问时，把问题也变成向量，去库里找最相似的几段；
4. 把这几段连同问题一起塞进提示词，让模型照着资料回答。

这样模型答的是你给的材料，能标出处，资料更新了也不用重训模型。RAG 出自 Lewis 等人 2020 年的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》（arXiv:2005.11401），已补入本仓第三卷（见[第三卷 · RAG 条目](../第三卷-Transformer与大模型.md)）。它和微调的分工要记清：**微调改的是说话方式和习惯，RAG 补的是事实和资料**，搞反了两边都不讨好。

### 护栏（guardrails）：给 Agent 上规矩

模型会犯错、会被诱导、会自信地胡说。护栏就是在程序侧立的规矩，常见的有：

- **进门检查**：用户输入先过滤，明显的注入攻击（"忽略你之前的指令……"）拦下来。
- **权限最小化**：只读的活就别给写权限；删文件、发邮件、付款这类不可逆动作，必须停下来等真人确认。
- **步数上限**：循环最多转 N 圈，超了就停。没有这条，Agent 能在一个死胡同里烧掉你一整晚的 API 额度。
- **出门检查**：最终答复过一遍再发出去——有没有泄漏不该说的、有没有编造的引用。
- **全程留痕**：每一步的 Thought、Action、Observation 都记日志。出问题时你能倒带看它错在哪一步，而不是对着黑盒子猜。

护栏不是一个模型或一个库，是你写程序时的纪律。这也呼应 [InstructGPT 精译](../全文精译/08-InstructGPT-2022.md) 里那条线：对齐（alignment）解决的是模型"愿不愿意"听话，护栏解决的是程序"能不能"兜底，两层都要有。

### 评估（eval）：别靠感觉，用题考它

Agent 做完，怎么知道它好不好？靠多跑几次觉得"还不错"，是最常见的自欺。评估的做法和考试一样：

1. 准备一套固定的测试题（20 到 50 条起步），每条带上你认可的标准答案或判定规则。
2. 每次改了提示词、换了模型、加了工具，把整套题重跑一遍，看成功率。
3. 分数掉了就是掉了，先查日志找原因，别急着用"这次运气不好"解释过去。

判定方式从土到洋：能用程序判死的（答案是不是某个数、文件有没有生成）就用程序判；开放性问题可以用另一个模型当裁判（LLM-as-judge），但裁判本身也会偏心、会被长答案讨好，所以关键题还是要留人工抽查。评估这件事的价值在于：**它让你敢改东西**。没有测试集，每次改动都是赌博；有了测试集，改错了立刻知道。

## 动手路线

顺序是刻意的：先裸手写，再上框架。框架替你做的事，你得先亲手做过一遍，才知道它替你做了什么。

### 第 1 步：裸 API 手写一个最小循环

- **目标**：不借助任何 Agent 框架，用一个大模型 API（哪家的都行，支持工具调用即可）手写出 ReAct 循环。
- **做什么**：一个 while 循环而已：维护一份消息列表 → 调模型 → 如果模型要调工具，就执行并把结果追加进消息列表，继续循环 → 如果模型给出最终答复，退出。自己定一个最大步数，比如 10 步。再加一条日志打印，把每一圈的进出都打出来。
- **预计时长**：一个晚上到周末半天。
- **过关标准**：你的程序能处理"模型连着调两次工具才回答"的情况；人为让工具报错，程序不崩、能把错误信息递回给模型；步数超限时能干净地停下来并说明原因。

### 第 2 步：加工具

- **目标**：让 Agent 真正能办事，并体会"工具是写给模型看的说明书"。
- **做什么**：加三个工具练手——计算器（算数别让模型心算）、查当前时间、读本地文件。重点练工具描述：名字、用途、参数说明要写得像给新同事的交接文档，模型全靠这段文字决定何时用、怎么传参。描述写含糊，模型就用得乱，这不是模型的错。
- **预计时长**：半天。
- **过关标准**：出十道题考它（"帮我算一下 (37+85)×12""我笔记里那篇讲备份的文章说了啥"），它能选对工具、传对参数；再故意问一件工具办不到的事，它应当承认办不到，而不是编一个结果出来。

### 第 3 步：加 RAG

- **目标**：让 Agent 能基于你自己的文档回答问题，并分清"资料里有"和"资料里没有"。
- **做什么**：拿一批自己的文档（本仓的论文导读就是现成的语料），按几百字一段切开，用一个 embedding 模型（API 或本地小模型都行）转成向量，存成一个简单的本地文件；提问时算一遍余弦相似度，取最像的 3 到 5 段拼进提示词。不急着上专门的向量数据库——几千段以内，一个文件加几行相似度计算就够用，先把原理跑通。
- **预计时长**：一天。
- **过关标准**：问文档里有的问题，它答对且能指出出自哪一篇；问一个文档里根本没有的问题，它会说"资料里没找到"，而不是顺口编。后面这一条比前面更重要。

### 第 4 步：加护栏与 eval

- **目标**：把玩具变成能放心用的东西，并建立"改一版、考一遍"的节奏。
- **做什么**：护栏加三样——危险工具（写文件、删文件）执行前打印出来等确认；循环步数上限落地；输入里出现明显的指令注入时拒绝执行。eval 做一套 20 条小题：一半考工具选择，一半考 RAG 问答，每条写好判定规则，能自动判的自动判。然后故意改坏一处（比如把计算器工具的描述删一半），重跑，看分数是不是真的掉了——掉了，说明你的评估是活的。
- **预计时长**：一天。
- **过关标准**：20 条题能一键跑完出分数；故意改坏后分数明显下降，改回来分数恢复；日志里能完整倒带任意一次运行的全过程。

### 第 5 步：最后再看框架

- **目标**：认识框架替你省了什么、又替你藏了什么，然后按需要选用。
- **做什么**：用 [LangChain](https://github.com/langchain-ai/langchain)（当前是 1.x 版本，建 Agent 用它的 `create_agent`）把你第 1 到 4 步的东西重写一遍，对照着看：你手写的循环、工具定义、状态管理，它各自用什么现成件替代了。需要更细的流程控制（分支、人工审批、长时间运行的任务）时，再看它底层的 LangGraph。在这一步之前，你应该已经能自己回答"框架值不值得学"——因为它省下的每一件事你都亲手干过。
- **为什么不先学框架**：三个原因。一，框架把循环藏起来了，没手写过的人出了问题只会干瞪眼，不知道是模型的问题、工具的问题还是框架的问题；二，框架版本变化快，API 隔几个月就换模样，地基概念（循环、工具、状态）十年不变，先学不变的；三，框架的文档默认你已经懂它在自动化什么，跳过手写直接学框架，多半会卡在"照着教程能跑、换个需求就不会"。
- **预计时长**：重写对照，两三天。
- **过关标准**：能说清自己手写版和框架版在结构上一一对应的关系；能判断一个新需求该用裸写、LangChain 还是 LangGraph，并说得出理由。

## 走完这条线的自检

1. 有人说"我们用了最先进的 Agent 模型"，你能追问出他其实想说的是哪一层吗？
2. 模型输出了一段要删文件的工具调用，文件为什么还没有被删？中间是谁在把关？
3. Agent 聊到第五十轮开始忘事，你先怀疑什么？
4. 用户问了一个你文档里没有的问题，Agent 答得头头是道——你的系统在哪一步本该拦住它？
5. 你改了提示词，感觉变好了。上线前你拿什么证明它真的变好了，而不是在另一些题上变差了？
6. 一个新框架号称"一行代码建 Agent"，你能说出那一行背后至少藏了哪四件事吗？
